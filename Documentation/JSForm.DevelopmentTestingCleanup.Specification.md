# JSForm DevelopmentTesting cleanup specification

Status: Approved and implemented

Approved by: Rev. Jonathan C. Watt

Verified: August 29, 2026 - 457 JSForm tests passed (2 skipped), 1,081
ChurchManager tests passed (25 skipped), and fresh wheel/source distribution
verification passed.

Date: August 29, 2026

Framework owner: JSForm

Application impact: None. ChurchManager behavior and its roadmap are out of
scope.

## 1. Purpose

Retire the legacy `DevelopmentTesting` directory without losing unique,
reusable JSForm behavior or weakening supported regression coverage. The
directory currently contains 36 tracked source artifacts (32 Python files and
4 JSON definitions) plus 32 generated bytecode files. Supported runtime code,
tests, documentation, and packaging contain no references to these files.

## 2. Safety boundary

- Treat every file as untrusted historical material until reviewed.
- Do not execute legacy scripts during classification.
- Do not connect to a database, network service, Word, or another external
  application while evaluating a file.
- Do not preserve credentials, connection strings, database contents,
  congregation data, absolute machine paths, logs, or generated bytecode.
- Do not move ChurchManager-specific behavior into JSForm.
- Preserve reusable public behavior only through supported JSForm modules,
  documentation, samples, schemas, and automated tests.

## 3. Required inventory

Create a review table containing every tracked file and these fields:

- relative path;
- apparent purpose;
- dependencies and side effects;
- corresponding supported implementation, test, or documentation, if any;
- classification;
- evidence supporting that classification; and
- resulting action.

Generated `*.pyc` and `__pycache__` content may be classified together as
generated debris, but its removal and ignore coverage must still be verified.

## 4. Classification rules

Each tracked source artifact shall receive exactly one classification:

1. **Replaced:** Supported code and tests already cover the behavior. Record the
   replacement paths, then delete the experiment.
2. **Migrate:** The artifact demonstrates useful framework behavior that lacks
   supported coverage. Reimplement the smallest application-neutral regression
   test or documentation example first, verify it, then delete the experiment.
3. **Historical only:** The artifact concerns an abandoned design, obsolete
   dependency, unsafe workflow, or one-time investigation and has no supported
   product value. Record the evidence, then delete it.
4. **Temporarily retained:** Evidence is insufficient to classify safely. State
   the exact unresolved question and required follow-up. This classification is
   exceptional and prevents completion of the cleanup roadmap item.

Filename, age, or lack of imports alone is not sufficient evidence for deleting
a tracked source artifact.

## 5. Migration requirements

Behavior selected for migration shall:

- be useful beyond one application screen;
- use the current public API and unified schema;
- avoid live credentials, databases, network access, GUI automation, and
  machine-specific paths in ordinary automated tests;
- use fake or isolated dependencies where practical;
- include a concise contract-focused test name and docstring; and
- pass before the historical artifact is deleted.

Exploratory visual behavior that cannot be meaningfully automated may become a
documented manual Windows wxPython acceptance check, but it must not be claimed
as visually verified unless rendered and inspected.

## 6. Removal and repository safeguards

After every tracked artifact is classified and all required migrations pass:

- delete the reviewed `DevelopmentTesting` sources and generated bytecode;
- remove the empty directory;
- retain distribution exclusion as defense in depth;
- add a repository test that fails if `DevelopmentTesting` returns;
- verify no supported source, test, documentation, manifest, or package points
  to the retired directory except the historical cleanup record and safeguard;
  and
- verify a fresh wheel and source archive contain no retired material.

## 7. Verification

Completion requires:

1. a complete 36-file review table with no temporarily retained entries;
2. passing focused tests for every migrated behavior;
3. passing JSForm source, schema, documentation, and distribution checks;
4. a fresh wheel and source archive with no `DevelopmentTesting`, `*.pyc`,
   credentials, logs, or database dumps;
5. the complete JSForm automated suite in a dependency-complete environment;
6. the complete ChurchManager suite as an integration regression gate; and
7. an updated JSForm roadmap entry recording the inventory result, migrations,
   removals, test counts, and any skipped environmental checks.

## 8. Approval gate

Approval of this specification authorizes the bounded inventory,
classification, necessary application-neutral test migrations, removal of
classified artifacts, documentation updates, and verification described above.
It does not authorize changes to ChurchManager or execution of legacy scripts.

Approval was received August 29, 2026. The complete inventory is recorded in
`JSForm.DevelopmentTestingCleanup.Inventory.md`. All 36 tracked artifacts and
32 generated bytecode files were removed with no behavior migrations required.
